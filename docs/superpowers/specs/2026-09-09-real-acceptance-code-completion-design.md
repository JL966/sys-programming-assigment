# 学习板真实验收代码闭环设计

日期：2026-09-09

## 1. 背景与结论

当前工程已具备固定 24 字节协议、CRC、PC 模拟验收、证据存储、报告导出、三角色 Keil 工程和 UART1 HELLO 实板记录，但尚未形成真实 Web Serial 到 CTRL/DUT/REF、板端计划执行、记录拉取和报告归档的完整代码链路。

本轮采用“验收闭环优先”方案：先完成可由自动测试证明的协议、编排、状态、安全与界面代码，再等待实板关闭硬件不确定性。没有实际板端记录的项目不得显示硬件 PASS。

## 2. 目标

本轮完成以下代码能力：

1. 网页可分别连接 CTRL、DUT、REF 三个 CH340 串口，并以 HELLO 响应核对角色、协议版本、固件版本、能力和板号。
2. 真实模式通过固定帧协议建立会话、提交冻结配置、运行计划、取消、复测、拉取记录并生成报告。
3. PC 端真实传输与现有模拟传输实现同一验收接口，界面和报告不需要维护两套业务流程。
4. 板端补齐 P0 所需命令、有限记录缓存、租约、人工确认和释放语义。
5. CTRL 作为唯一计划控制者；PC 对 DUT/REF 的独立 USB 默认只做身份核验、状态与证据读取，不同时驱动同一硬件动作。
6. 建立使用真实协议帧的虚拟三板环境，在无实板时覆盖端到端成功、故障、超时、断线、取消、重连和记录生命周期。
7. 三角色 Keil 工程继续生成可烧录 HEX，软件与构建检查纳入统一门禁。

## 3. 非目标与真实性边界

- 本轮不宣称 RS485、红外、RTC、EEPROM、传感器已经实板通过。
- 不实现自动烧录、元件级故障定位或任意脚本下发。
- 不加入 FM、音乐、直流电机和步进电机等高风险非核心能力。
- 不以模拟器结果替换真实模式记录；真实模式缺少设备、能力或记录时返回 BLOCKED 或 INCONCLUSIVE。
- 不使用破解工具；仅使用当前可工作的 Keil 环境进行构建。
- 不在未获得原值快照确认前执行 EEPROM 写入，不允许运行计划隐式授予写入权限。

## 4. 总体架构

```text
网页 UI
  │
  ├── AcceptanceEngine ──统一计划、attempt、诊断和报告模型
  │       ├── SimulatedRig ──软件演示
  │       └── RealRig ───────真实协议编排
  │               │
  │        NodeConnectionManager
  │          ├── CTRL ProtocolClient ─ Web Serial
  │          ├── DUT  ProtocolClient ─ Web Serial（独立诊断）
  │          └── REF  ProtocolClient ─ Web Serial（独立诊断）
  │
  └── EvidenceStore ──运行、原始帧、记录分片、人工决定和导出

CTRL 固件
  ├── 固定帧收发与命令状态机
  ├── 计划调度器和安全租约
  ├── UART2/RS485 节点事务
  ├── 有限记录缓存
  └── 测试适配器接口
        ├── UART1/RS485/IR
        ├── RTC
        ├── EEPROM 安全状态机
        └── 性能快照
```

PC 是操作、归档和解释端，CTRL 是运行时唯一计划主控，DUT 是被测端，REF 是参考激励端。三者职责遵循原详细实施设计，不把 USB 直连成功冒充 RS485 或红外通过。

## 5. PC 端组件

### 5.1 ProtocolClient

`ProtocolClient` 位于新增的独立模块中，负责：

- 维护每连接单调递增的 `seq`；
- 编码请求并通过 `SerialTransport` 串行发送；
- 使用 `FrameStreamDecoder` 从任意分片字节流恢复帧；
- 按 `src/dst/session/seq/type` 匹配响应；
- 只读命令允许同 seq 有限重试，动作命令不生成新 seq 重做动作；
- 将 CRC 错误、错误目标、陈旧会话、超时和断线转换为可诊断错误；
- 关闭时拒绝所有未完成请求并释放 Web Serial 锁。

协议 ACK 仅表示命令已接受，不直接生成测试 PASS。

### 5.2 NodeConnectionManager

连接管理器持有 CTRL、DUT、REF 三个槽位。每次用户选择串口后立即发送 HELLO：

- 角色不匹配时拒绝绑定；
- 协议版本不匹配时拒绝进入 READY；
- 同一角色或同一串口重复绑定时给出明确错误；
- 板号、角色、固件和能力写入当前运行快照；
- 任何端口断开时更新节点状态，并使依赖该节点但尚未开始的项目 BLOCKED。

快速核心计划要求 CTRL 连接。需要独立 USB 证据的 T01 目标节点和细分定位项目，还要求对应 DUT/REF 连接；缺少独立端口时允许 CTRL 转发证据，但报告降低定位等级。

### 5.3 RealRig

`RealRig` 实现与 `SimulatedRig` 相同的 `preflight()`、`runTest()`、`cancel()` 和 `close()` 契约：

1. 预检三角色和能力；
2. 生成非零 session、run_tag 和规范化配置 CRC；
3. 对 CTRL 建立会话并提交配置；
4. 向 CTRL 发送单项 test mask 的 RUN_PLAN；
5. 轮询状态并拉取该 attempt 的记录分片；
6. 校验记录头、长度、分片一致性和 body CRC；
7. 从真实记录构造 attempt，交由现有诊断与报告模块处理；
8. 确认持久化成功后发送 RELEASE_RESULT。

复测始终产生新 attempt，并保留 `parentAttempt`。取消发送整轮或当前 attempt 的 CANCEL_TEST；串口状态不确定时先查询 GET_STATUS，不盲目重发动作。

### 5.4 页面交互

真实模式增加以下界面元素：

- CTRL/DUT/REF 三个连接按钮、连接状态和身份信息；
- 串口兼容性、端口占用、角色错误和断线提示；
- 运行前检查清单与能力缺口；
- EEPROM 写入授权复选框，默认关闭且每轮重置；
- ASSISTED_AUTO 操作提示；
- MANUAL 项目的“通过/不通过/无法确认”按钮和操作者标记；
- 真实帧计数、CRC 错误、重试和最近事件日志。

模拟模式继续保留故障注入，但相关控件在真实模式下禁用。切换来源不会把模拟 attempt 混入真实运行。

## 6. 板端代码闭环

### 6.1 命令状态机

补齐以下消息处理：

- GET_STATUS：返回阶段、attempt、当前测试、原因和错误计数分页；
- CONFIG_WRITE：保存白名单键和值并校验范围；
- CONFIG_COMMIT：按规范顺序计算并核对 CRC，运行期间冻结；
- READ_RECORD：按四字节数据片返回有限记录；
- HUMAN_CONFIRM：只接受当前等待人工决定的 attempt；
- RELEASE_RESULT：仅释放已持久化确认的当前记录；
- RENEW_LEASE：仅允许当前 attempt 且不突破单项动作上限；
- LINK_CHALLENGE：回显 trial、pattern CRC 和计数；
- CLOSE_SESSION、取消、暂停与恢复执行幂等清理。

未知命令、错误状态、错误会话、错误 attempt 和越界参数必须返回明确状态码且不改变业务状态。

### 6.2 计划调度器

CTRL 的 RUN_PLAN 不再只切换为 RUNNING，而是建立单项任务并通过非阻塞 tick 推进：

```text
PREFLIGHT → PREPARE → ARM → EXECUTE → COLLECT → EVALUATE
                                            ↓
DONE ← RECORD ← CLEANUP ← TIMEOUT/CANCEL/ERROR
```

每个阶段都有超时和清理出口。CTRL 对 UART2 保持单主；动作租约到期自动停止并保存失败原因。PC 断开不清除正在清理的 EEPROM 恢复状态。

### 6.3 有限记录缓存

每个节点至少保留一条当前 attempt 结果记录和一条原始证据记录。记录使用显式字节布局，不序列化 C 结构体内存。缓存满时返回 BUFFER_FULL，不覆盖尚未 RELEASE 的记录。

首轮必须实现结果、通信、RTC、存储和性能五类记录的编码/解码测试。ADC 与人工事件记录沿用同一头部，按后续适配器逐项启用。

### 6.4 P0 测试适配器

- T01：各节点 UART1 固定模式挑战和往返证据；
- T02：CTRL 在 UART2 上调度 REF→DUT 与 DUT→REF 的 LINK_CHALLENGE；
- T03：实现 BSP IR 的准备、单向窗口、反向窗口和原始 12 字节证据；
- T04：非阻塞读取 RTC BCD，保存起止值和 MCU 经过时间；
- T05：限定 `0x10..0x1F`，执行读取快照、等待 SNAPSHOT_ACK、模式写入、读回、恢复和恢复校验；
- T14：记录 `GetSysPerformance()` 的 MainLoops、PollingMisses 和通信溢出计数。

所有适配器先完成编译和主机侧纯逻辑验证。未下板前，发布说明把它们标为“代码就绪、硬件待验证”，不预置 PASS 记录。

## 7. 虚拟三板集成环境

新增 `VirtualBoard` 和 `VirtualSerialPort` 测试工具。它们必须消费和生成真实 24 字节帧，通过与浏览器相同的 ProtocolClient 交互，而不是直接返回 attempt 对象。

虚拟环境覆盖：

- 三角色 HELLO 和错误角色拒绝；
- 分片、粘包、垃圾字节和 CRC 错误恢复；
- 会话、配置 CRC、计划和记录拉取；
- T01–T05 正常路径；
- RS485/IR 超时、RTC 停止、EEPROM 不一致与恢复失败；
- 重复动作请求的幂等响应；
- 断线、重连、陈旧会话、错误 attempt；
- 取消和租约到期后输出停止；
- 记录分片重复去重、冲突拒绝和释放顺序。

虚拟板结果的 `source` 固定为 `VIRTUAL_PROTOCOL`，只用于代码集成验证，报告必须显示非硬件证据。

## 8. 错误处理与安全

- 浏览器不支持 Web Serial、端口被占用或用户取消选择时不破坏已有连接。
- 响应超时保留请求帧、重试次数和经过时间；前提未建立为 BLOCKED，已建立后目标未响应才可 FAIL。
- CRC 或分片冲突使记录无效，不生成 PASS。
- EEPROM 测试需要当前会话写入授权、PC 已保存原值、匹配的 SNAPSHOT_ACK 和板端范围复核。
- 恢复失败设置 RESTORE_REQUIRED，阻止后续存储写并在页面持续显示。
- 人工确认必须记录操作者、决定和时间；人工 PASS 不计入自动 PASS。
- 所有真实模式报告包含板号、角色、固件版本、协议版本、配置 CRC、来源和能力缺口。

## 9. 测试与验证

### 9.1 JavaScript

- 协议事务：响应匹配、超时、重试、断线和关闭；
- 三角色连接：角色/版本/重复端口校验；
- 记录分片：完整、重复、缺失、冲突和 CRC；
- RealRig：预检、配置、运行、取消、复测和释放；
- 虚拟三板端到端：正常和故障路径；
- 存储与报告：来源隔离、人工决定和安全状态。

### 9.2 C 与 Keil

- 每个新增命令至少一条合法向量和一条非法状态/边界向量；
- 调度器正常、超时、取消、租约和恢复状态测试；
- 记录编码/分片/释放测试；
- EEPROM 地址、长度、授权和恢复门禁测试；
- GCC 主机测试通过后，三角色 Keil 工程均须 `0 Error(s)` 并生成 HEX；
- 对新增 warning 逐条判断，已知未调用 BSP 段在文档中说明。

### 9.3 浏览器

通过可控的虚拟 Web Serial 注入验证：三角色连接、快速计划、故障、复测、人工确认、取消、导出和断线提示。桌面与移动视口不得横向溢出，控制台不得出现未处理错误。

### 9.4 真实性门禁

自动测试只证明代码和虚拟协议链路。实板记录目录没有对应运行证据时，文档和 UI 不得把 T02–T05 标为硬件通过。未来下板按 G0→G1→G2→G3 顺序关闭这些门禁。

## 10. 交付与验收条件

本轮代码交付完成需同时满足：

1. 模拟、虚拟协议、真实串口三种来源有明确且不可混淆的标识；
2. 真实页面可以完成三角色连接和身份核验；
3. RealRig 可通过虚拟串口完成快速核心计划并生成可复算报告；
4. 板端新增命令、调度器和记录生命周期通过 C 测试；
5. EEPROM 安全门禁和取消清理有失败路径测试；
6. 三个 Keil 工程构建成功并输出 HEX；
7. 软件全量门禁和浏览器流程通过；
8. README、软件验证记录和下板手册统一描述当前真实状态；
9. Git 工作区只包含本轮相关改动，并推送到远端仓库。

## 11. 后续下板阶段

代码完成后仍需用户在实板上依次执行：

1. 三角色 UART1/HELLO 回归；
2. 双板与三板 RS485；
3. 红外正常、遮挡、恢复；
4. RTC 时间推进；
5. EEPROM 备份、写入、恢复和掉电检查；
6. 根据实际板卡能力再启用温光、超声波和人工声光输入。

只有对应记录文件、固件哈希和现场条件齐全后，才能更新硬件验收结论。
